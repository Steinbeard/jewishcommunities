# =====================================================================
# Kehillah task contracts -- v8 spec (docs/spec/v8-task-contracts.md).
#
# Four contract types letting a non-Kehillah (in practice: non-Jewish)
# ruler offer work to a Kehillah community leader through CK3's real EP3
# Task Contracts system, rather than a bespoke decision-based mechanic --
# the user's own explicit preference for the loan case ("I think I
# prefer the contract mechanic for loans over a decision! Feels more
# compelling and character driven"), extended to the other three for
# consistency.
#
# MECHANICS CONFIRMED AGAINST THE INSTALLED GAME FILES BEFORE WRITING
# ANY OF THIS, NOT ASSUMED:
#   - _task_contracts.info (this same folder) is the field template.
#   - create_task_contract / accept_task_contract / complete_task_contract
#     are plain effects usable from any decision/event/on_action effect
#     block -- confirmed via common/character_interactions/
#     06_ep3_laamp_interactions.txt's contact-list "request a contract"
#     flow (random_list of contract types gated by can_create_task_contract,
#     each branch calling create_task_contract = { task_contract_type
#     task_contract_tier location task_contract_employer save_scope_as }),
#     common/character_interactions/00_debug_interactions.txt, and
#     common/council_tasks/00_spymaster_tasks.txt (task_contract_tier and
#     location confirmed REQUIRED fields on create_task_contract, not
#     optional, even for a travel = no contract -- every real call site
#     checked sets both).
#   - task_contract_taker / task_contract_employer / task_contract_target
#     are built-in links readable off a TASK_CONTRACT scope (root, inside
#     on_create/on_accepted/on_completed/on_invalidated/task_contract_reward
#     effect blocks -- confirmed via admin_contracts.txt's own on_accepted/
#     task_contract_reward bodies, which universally open with
#     save_scope_as = task_contract before reading task_contract_taker /
#     scope:task_contract.task_contract_employer). Once you switch INTO
#     task_contract_taker (a character scope), the contract's other links
#     are no longer directly reachable -- admin_contracts.txt always reads
#     them back off the saved scope:task_contract, not by re-chaining off
#     the character. Followed identically below.
#   - "target" IS a real, distinct create_task_contract parameter from
#     "employer" -- confirmed via common/council_tasks/00_marshal_tasks.txt
#     and common/factions/10_tgp_factions.txt (target = scope:councillor_
#     liege / scope:faction.faction_target) and read back as the built-in
#     task_contract_target link (common/character_interactions/
#     06_ep3_laamp_interactions.txt's complete_task_contract_interaction:
#     "task_contract_target ?= scope:recipient"). This answers v8 spec
#     section 4d's open question: yes, kehillah_hebrew_tutor_contract can
#     name a specific pupil distinct from the employer who commissioned
#     the tutoring.
#   - invalidate_contract = yes (NOT "invalidate_task_contract = <scope>",
#     the name the spec's own draft guessed) is the real effect, called ON
#     a task_contract scope -- confirmed via common/scripted_effects/
#     09_mpo_settlement_issue_effects.txt ("scope:contract = {
#     invalidate_contract = yes }" in the AI-decline branch of
#     settlement_issue_on_create_effect) and common/casus_belli_types/
#     07_ep3_wars.txt. "invalidate_task_contract" does not exist anywhere
#     as a callable effect in the installed files -- only inside this
#     very _task_contracts.info comment block and one unrelated
#     effect_localization entry that documents invalidate_contract's own
#     display text. The spec explicitly flagged this name as unverified
#     ("whichever the agent finds cleaner ... verify before choosing, do
#     not guess") -- verified, and corrected here.
#   - NO clean vanilla precedent exists for create_artifact-family effects
#     INSIDE a task_contract_reward block. The one create_artifact call in
#     the entire common/task_contracts/ folder (laamp_extra_contracts.txt's
#     treasure-map contract) runs in on_accepted, not in a reward. Per the
#     spec's own instruction ("if none exists cleanly, gold + opinion is a
#     perfectly fine scope cut, document it as such rather than forcing an
#     artifact in"), kehillah_exotic_goods_contract below is gold + opinion
#     only -- see that type's own header for the full note.
#   - This whole system is EP3 (Legacy of Persia) content at the engine
#     level, not just UI-gated vanilla content that happens to live under
#     common/task_contracts/ -- has_ep3_dlc_trigger (common/
#     scripted_triggers/00_has_dlc_scripted_triggers.txt) gates every
#     valid_to_create below and the pulse's own on_action trigger
#     (common/on_action/kehillah_on_actions.txt), mirroring this mod's own
#     established has_ce1_dlc_trigger pattern on kehillah_epidemic_pulse
#     rather than assuming EP3 the way nothing else in this mod does.
#
# GROUP: all four share one new group (kehillah_contract_group) rather
# than each getting its own -- no common/task_contract_groups-style
# registry file exists in the installed game (grepped for one and found
# none; "group" on admin_governance_group, laamp_contracts_*, etc. is
# used across dozens of vanilla contract types with no defining file
# anywhere), so it is a free-form UI-grouping label, not a validated
# reference. "So they render together" (spec section 4's own phrasing)
# means one shared group, not four separate ones.
#
# WEIGHT = 0 ON ALL FOUR, DELIBERATELY. weight only matters to vanilla's
# own populate_task_contracts_for_area auto-population algorithm (see
# common/scripted_effects/07_dlc_ep3_scripted_effects.txt), which this
# mod never calls -- every Kehillah contract is created explicitly, by
# name, from events/kehillah_task_contract_events.txt. Leaving weight at
# the template's own default (0) means these types can never accidentally
# get swept into vanilla's regional auto-population if that system ever
# runs near a Kehillah quarter, without needing a fragile negative trigger
# to keep them out.
#
# OFFER FLOW, DECLINE HANDLING, AND SKILL-TIER RESOLUTION are all
# implemented in events/kehillah_task_contract_events.txt -- see that
# file's own header for the full account of how a contract is offered,
# accepted or declined, and (for the three non-loan types) resolved
# immediately in the same accept step via on_accepted itself calling
# complete_task_contract directly, once verified against admin_contracts.
# txt's own confirmed on_accepted/on_completed split for a non-travel
# contract (on_accepted does the work, on_completed is empty, the reward
# is applied by complete_task_contract naming a task_contract_reward key
# -- see overdue_taxes in the installed admin_contracts.txt for the
# precedent this mirrors).
# =====================================================================


# ---------------------------------------------------------------------
# TRANSLATION -- commission a translation of a real Greek or Arabic work
# into Latin. v8 spec section 4a; overhauled top-to-bottom in v11, at
# the user's own explicit request, into a genuine multi-stage challenge.
# See events/kehillah_translation_events.txt (the challenge chain itself)
# and common/scripted_effects/kehillah_translation_effects.txt (the
# effects it calls) for the full mechanical account; this header covers
# what changed here, in the contract TYPE definition, and why.
#
# CREATION-SIDE GATE UNCHANGED (spec 4a, v8): valid_to_create is still
# learning >= 8 OR kehillah_rabbi_trait -- "some baseline learning
# skill... or the kehillah_rabbi_trait," the spec's own suggested
# either/or, matching kehillah_compose_commentary_decision's own bar for
# "can attempt serious scholarship" (common/decisions/kehillah_
# decisions.txt).
#
# THE EMPLOYER GATE IS NEW (v11, "this contract should only be offered
# by non-Muslim non-Greek rulers"): moved onto scope:employer INSIDE
# valid_to_create rather than only valid_to_accept, specifically so it
# also gates the ROUTER's own can_create_task_contract check (events/
# kehillah_task_contract_events.txt's kehillah_task_contract.0001 passes
# employer = scope:employer into that check, per this file's own top
# header -- so valid_to_create, not just valid_to_accept, is what
# actually controls whether this type is even offered to a given
# candidate). In-fiction: a Muslim ruler's own clerks already read
# Arabic, and a Greek/Byzantine-heritage ruler's own clerks already read
# Greek, so neither would need the Kehillah to render one INTO Latin.
# Checked against real, confirmed trigger keys, not guessed -- faith.
# religion = religion:islam_religion is this mod's own already-
# established idiom (common/scripted_triggers/jewish_holiday_scripted_
# triggers.txt's identical faith.religion = religion:judaism_religion),
# and culture = { has_cultural_pillar = heritage_byzantine } is the
# real, extensively precedented vanilla trigger for "this culture reads
# Greek" (grepped: heritage = heritage_byzantine as a direct comparison
# appears NOWHERE in the installed game; has_cultural_pillar is what
# every one of hundreds of real call sites actually uses, culture-only
# and heritage-based rather than religion-based on purpose, since a
# Greek Muslim or Greek Jewish character would still read Greek).
#
# THE OFFER NOW NAMES A SPECIFIC WORK (v11, "should name specific books
# from a list of Greek and Arabic real medieval works that are pre-876,
# or books... owned by Arab or Byzantine rulers"): picked by kehillah_
# translation_pick_work_effect (common/scripted_effects/kehillah_
# translation_effects.txt) in the ROUTER, before the flavored offer
# event fires, so the offer itself (kehillah_task_contract.0002) can
# name it. See that effect's own header for the ten real works chosen
# and their dating.
#
# "MORE LEARNED RULERS REQUEST IT" (v11) is implemented in the ROUTER's
# own random_list weighting (events/kehillah_task_contract_events.txt),
# not here -- this type has only ever offered ONE candidate employer per
# pulse (the community's own local county holder, kehillah_has_task_
# contract_employer_candidate_trigger), so "more learned rulers request
# it" cannot mean widening a candidate POOL; it means that SAME
# candidate is more likely to be the one THIS contract type gets rolled
# for, the one lever the existing one-candidate architecture actually
# has. See that file's own updated header.
#
# NO LONGER RESOLVED IMMEDIATELY (v11, "make the translation actually a
# challenge... a series of challenges that determine success or
# failure"). on_accepted now only sets a starting tally (from the SAME
# learning/rabbi-trait either/or valid_to_create already gates on, three
# baseline bands instead of a flat start) and a hand-off to events/
# kehillah_translation_events.txt's own four-stage chain, instead of
# branching straight to complete_task_contract. This makes translation
# the SECOND task_contract_type in this file not resolved inside its own
# on_accepted, after kehillah_loan_contract -- unlike the loan, though,
# nothing here is reusing an untouched pre-existing system, so there was
# no equivalent constraint to honor; the chain is new, purpose-built.
#
# THREE REWARD TIERS, NOT TWO, PLUS A SEPARATE STOLEN PAIR (v11). TRIUMPH
# and SUCCESS both still pay the flat kehillah_translation_greatness_
# reward (kehillah_script_values.txt's own updated note on that value
# explains why); FAILURE -- new, the actual "or failure" half of the
# request -- pays a token fee and a mild opinion hit instead of a gain.
# translation_stolen_caught/_undetected are the two endings of "a final
# decision to steal the book vs complete the contract" (kehillah_
# translation.0005's own "Keep the true copy" option, kehillah_
# translation_steal_effect) -- an artifact IS created for that ending
# (create_artifact_book_effect, called from the EVENT option itself,
# BEFORE complete_task_contract fires), which does not violate this
# file's own earlier "no create_artifact precedent inside a task_
# contract_reward block" finding (still true, still honored: the
# artifact is created in the calling EVENT, not inside the reward
# block's own effect body below).
# ---------------------------------------------------------------------

kehillah_translation_contract = {
	group = kehillah_contract_group
	icon = "gfx/interface/icons/artifact/artifact_book.dds"
	desc = kehillah_translation_contract_desc
	task_contract_request = kehillah_translation_contract_request

	travel = no
	is_criminal = no
	use_diplomatic_range = no

	valid_to_create = {
		has_ep3_dlc_trigger = yes
		government_has_flag = government_is_kehillah
		is_adult = yes
		is_imprisoned = no
		OR = {
			learning >= 8
			has_trait = kehillah_rabbi_trait
		}
		scope:employer = {
			NOT = { faith.religion = religion:islam_religion }
			NOT = { culture = { has_cultural_pillar = heritage_byzantine } }
		}
	}

	valid_to_accept = {
		scope:employer = {
			is_alive = yes
			NOT = { government_has_flag = government_is_kehillah }
			NOT = { faith = root.faith }
			NOT = { faith.religion = religion:islam_religion }
			NOT = { culture = { has_cultural_pillar = heritage_byzantine } }
		}
	}

	valid_to_continue = {
		task_contract_taker = { is_alive = yes is_imprisoned = no }
	}

	valid_to_keep = {
		task_contract_taker = { is_alive = yes }
	}

	on_create = {}

	# Hands off to events/kehillah_translation_events.txt's own four-
	# stage challenge chain instead of resolving in place -- see this
	# type's own header above for the full account of why. save_scope_as
	# = task_contract, then grabbing task_contract_employer BEFORE
	# switching into task_contract_taker, mirrors admin_contracts.txt's
	# own confirmed pattern (this file's top header, point 2) exactly;
	# both saved scopes are proven to survive the whole cross-event,
	# multi-week chain by the identical precedent kehillah_book_send_
	# copies_effect already established for scope:kehillah_book_author
	# (common/scripted_effects/kehillah_translation_effects.txt's own
	# header spells this out in full).
	on_accepted = {
		save_scope_as = task_contract
		task_contract_employer = { save_scope_as = kehillah_translation_employer }
		task_contract_taker = {
			play_sound_effect = "event:/DLC/EP3/SFX/UI/Contracts/ep3_ui_contracts_accept_contract"
			if = {
				limit = { learning >= 18 }
				set_variable = { name = kehillah_translation_tally value = kehillah_translation_baseline_high }
			}
			else_if = {
				limit = {
					OR = {
						learning >= 12
						has_trait = kehillah_rabbi_trait
					}
				}
				set_variable = { name = kehillah_translation_tally value = kehillah_translation_baseline_mid }
			}
			else = {
				set_variable = { name = kehillah_translation_tally value = kehillah_translation_baseline_low }
			}
			trigger_event = { id = kehillah_translation.0001 days = 5 }
		}
	}

	on_completed = {}

	on_invalidated = {
		task_contract_taker ?= {
			custom_tooltip = kehillah_task_contract_fell_through_tt
		}
	}

	should_show_toast_on_complete = yes

	task_contract_reward = {
		translation_triumph = {
			should_print_on_complete = yes
			visible = yes
			positive = yes
			effect = {
				save_scope_as = task_contract
				task_contract_taker = {
					play_sound_effect = "event:/DLC/EP3/SFX/UI/Contracts/ep3_ui_contracts_success_on_contract"
					add_gold = major_gold_value
					reverse_add_opinion = {
						target = scope:task_contract.task_contract_employer
						modifier = flattered_opinion
						opinion = 40
						years = 5
					}
					primary_title = {
						change_variable = { name = kehillah_var_greatness add = kehillah_translation_greatness_reward }
					}
				}
				custom_tooltip = kehillah_translation_triumph_tt
			}
		}
		translation_success = {
			should_print_on_complete = yes
			visible = yes
			positive = yes
			effect = {
				save_scope_as = task_contract
				task_contract_taker = {
					play_sound_effect = "event:/DLC/EP3/SFX/UI/Contracts/ep3_ui_contracts_success_on_contract"
					add_gold = medium_gold_value
					reverse_add_opinion = {
						target = scope:task_contract.task_contract_employer
						modifier = pleased_opinion
						opinion = 20
						years = 5
					}
					primary_title = {
						change_variable = { name = kehillah_var_greatness add = kehillah_translation_greatness_reward }
					}
				}
				custom_tooltip = kehillah_translation_success_tt
			}
		}
		translation_failure = {
			should_print_on_complete = yes
			visible = yes
			positive = no
			effect = {
				save_scope_as = task_contract
				task_contract_taker = {
					add_gold = minor_gold_value
					reverse_add_opinion = {
						target = scope:task_contract.task_contract_employer
						modifier = disappointed_opinion
						opinion = -15
						years = 3
					}
				}
				custom_tooltip = kehillah_translation_failure_tt
			}
		}
		translation_stolen_undetected = {
			should_print_on_complete = yes
			visible = yes
			positive = yes
			effect = {
				save_scope_as = task_contract
				# Re-saved here, fresh, rather than trusted to still carry
				# over from on_accepted's own much-earlier save -- ck3-tiger
				# flagged [kehillah_translation_employer...] in this reward's
				# own custom_tooltip as an unrecognized datafunction when it
				# only relied on the distant on_accepted save, even though
				# the script side itself checked out with zero errors. A
				# local save, right here in the same effect body the
				# tooltip fires from, is the same idiom this whole reward
				# block already uses for scope:task_contract itself.
				task_contract_employer = { save_scope_as = kehillah_translation_employer }
				task_contract_taker = {
					add_gold = minor_gold_value
					primary_title = {
						change_variable = { name = kehillah_var_greatness add = kehillah_translation_steal_greatness_reward }
					}
				}
				custom_tooltip = kehillah_translation_stolen_undetected_tt
			}
		}
		translation_stolen_caught = {
			should_print_on_complete = yes
			visible = yes
			positive = no
			effect = {
				save_scope_as = task_contract
				task_contract_employer = { save_scope_as = kehillah_translation_employer }
				task_contract_taker = {
					reverse_add_opinion = {
						target = scope:task_contract.task_contract_employer
						modifier = angry_opinion
						opinion = -40
						years = 8
					}
				}
				custom_tooltip = kehillah_translation_stolen_caught_tt
			}
		}
	}

	weight = {
		value = 0
	}
}

# =====================================================================
# LOAN CONTRACT -- ledger integration, AND a real challenge chain. v8
# spec section 5 originally defined the ledger integration; DIRECTION
# REVERSED 2026-09-17 at the user's own explicit request ("Wait it
# should be that you loan money to them!"), and a challenge chain added
# in the same pass ("an event chain with challenges to succeed").
#
# THE KEHILLAH IS THE LENDER, NOT THE BORROWER. root/task_contract_taker
# (the Kehillah ruler, still the contract owner) lends gold to
# scope:employer (a non-Kehillah, non-coreligionist neighbor), who
# becomes the BORROWER. This restores kehillah_extend_loan_decision's
# ORIGINAL direction (root = lender, target = borrower) -- the v8 build
# had inverted it (root = borrower, employer = lender) when first
# converting the decision into a task contract; see this file's own git
# history for that earlier version's (now superseded) reasoning.
#
# THE INVERSION WAS A REAL, LIVE BUG, NOT JUST A DIRECTION PREFERENCE --
# traced end to end while making this change. kehillah_loan_debtors (a
# variable_list) is walked every quarter by the accrual/default block
# inside kehillah_quarterly_pillars_effect (common/scripted_effects/
# kehillah_scripted_effects.txt, ~line 1867), which processes
# primary_title's OWN debtors list. That block only ever runs via
# kehillah_quarterly_pulse (common/on_action/kehillah_on_actions.txt),
# gated government_has_flag = government_is_kehillah -- it never fires
# for a non-Kehillah character. Under the inverted design, on_accepted
# added the Kehillah (the borrower, under that design) to the EMPLOYER's
# own kehillah_loan_debtors list -- since the foreign employer never
# gets kehillah_quarterly_pulse, that list was never walked: years_
# elapsed never incremented, loans never came due, and the default
# codepath was dead for every loan originated through the contract. This
# confirms kehillah_script_values.txt's own stated intent ("THE LENDER
# IS THE TITLE" note, ~line 793) that the LENDER's title is meant to
# hold the debtors list -- true only, and only ever working correctly,
# with the Kehillah as lender.
#
# THE EXISTING LEDGER IS STILL REUSED VERBATIM, NOT DUPLICATED --
# unchanged by the reversal. kehillah_loan_amount_owed / kehillah_loan_
# lender_title / kehillah_loan_years_elapsed are still written with the
# exact same values as before; only WHICH character they land on has
# changed (scope:employer, the borrower, instead of root). kehillah_
# loan_debtors still lives on the lender's title (now correctly the
# Kehillah's own, restoring the successor-safety property kehillah_
# script_values.txt's own header describes). kehillah_repay_loan_
# decision (common/decisions/kehillah_decisions.txt) and the quarterly
# accrual/default block are STILL completely untouched -- both already
# operate on "whichever character holds var:kehillah_loan_amount_owed,"
# with no assumption baked in about who that is, so restoring the
# original direction needed zero edits to either; they simply start
# working as originally intended.
#
# THE PROSPERITY GATE KEEPS ITS ORIGINAL, SIMPLER MEANING. Now that root
# is the lender again, kehillah_pillar_at_least_trigger's Healthy+
# Prosperity check on valid_to_create reads exactly as it did before the
# v8 inversion: is this community prosperous enough to have money to
# lend out at all. Same threshold, no new value.
#
# THE "NO SECOND LOAN" GUARD MOVES TO THE BORROWER. Previously NOT =
# { exists = var:kehillah_loan_amount_owed } sat on root (then the
# borrower); it now sits on scope:employer inside valid_to_accept (the
# borrower again, just relocated). Root's own valid_to_create no longer
# carries this guard at all -- the Kehillah can lend to several
# different borrowers at once (that is what kehillah_loan_debtors being
# a variable_list, plural, was always for); only lending TWICE TO THE
# SAME BORROWER is disallowed. A gold >= kehillah_loan_principal_value
# affordability check is added to both valid_to_create and valid_to_
# accept (root side) instead, since the Kehillah is now the one paying
# out, not receiving.
#
# NEW, 2026-09-17: A REAL CHALLENGE CHAIN, at the user's explicit
# request, mirroring kehillah_translation_contract's own v11 overhaul
# (events/kehillah_translation_events.txt) but lighter -- three events,
# own namespace kehillah_loan_challenge (events/kehillah_loan_events.txt),
# kept visually distinct from the many existing kehillah_loan_* ledger
# names. on_accepted no longer originates the loan immediately; it sets
# a Stewardship-banded starting tally (same three-band shape kehillah_
# translation_contract's own on_accepted already uses for Learning) and
# hands off to the chain. The chain's final event resolves the tally
# into SUCCESS or FAILURE -- two tiers, not three; "does the loan happen
# at all" is the one meaningful stake for a financial negotiation,
# unlike a scholarly triumph/success/failure spread -- and, ONLY on
# SUCCESS, runs the exact origination effect that used to live directly
# in on_accepted (same values, same shape, just relocated with taker/
# employer swapped). FAILURE pays out nothing and writes nothing to the
# ledger; the deal simply falls through, via the same invalidate_
# contract = yes effect already confirmed for a declined offer.
#
# SPEC SECTION 5 POINT 2 -- THE REPAYMENT-TRACKING DESIGN -- STILL
# HOLDS, UNCHANGED BY THE REVERSAL. Nothing calls complete_task_contract
# on this type, ever, for the same reason as before: kehillah_repay_
# loan_decision (untouched, per this task's own explicit constraint) and
# the quarterly default block are the only two things that ever clear
# the ledger variables, and neither leaves a surviving signal that would
# let this contract tell repayment and default apart after the fact.
# valid_to_continue/valid_to_keep track whether the loan is still open by
# checking task_contract_employer (the borrower) for exists/NOT exists
# var:kehillah_loan_amount_owed -- the same shape as before, just reading
# the correct character now. on_invalidated still fires a single NEUTRAL
# closing note once the debt clears either way, for the same reason as
# before: this contract genuinely cannot tell success from default
# without touching one of the two untouched files. This IS a real,
# documented scope cut, not an oversight: the authoritative record of
# what happened (the gold changing hands, the Prosperity/Greatness swing)
# is already fully visible to the player through the existing, unmodified
# UI at the moment it actually occurs.
#
# task_contract_reward IS STILL DEFINED, for the same "defense in depth"
# reason as before (in case anything ever does call complete_task_
# contract on this type in the future), and is still DELIBERATELY EMPTY
# of any prosperity/greatness/gold change -- those numbers are already,
# and must remain, applied exactly once by the untouched kehillah_repay_
# loan_decision and quarterly-default code paths, plus now the chain's
# own SUCCESS-only origination effect. Duplicating any of them here would
# double-book the ledger. The key exists so the type is well-formed and
# self-documenting, not because it is expected to fire.
# =====================================================================

kehillah_loan_contract = {
	group = kehillah_contract_group
	icon = "gfx/interface/icons/message_feed/money.dds"
	desc = kehillah_loan_contract_desc
	task_contract_request = kehillah_loan_contract_request

	travel = no
	is_criminal = no
	use_diplomatic_range = no

	valid_to_create = {
		has_ep3_dlc_trigger = yes
		government_has_flag = government_is_kehillah
		is_adult = yes
		is_imprisoned = no
		gold >= kehillah_loan_principal_value
		kehillah_pillar_at_least_trigger = { PILLAR = kehillah_var_prosperity THRESHOLD = kehillah_band_healthy_threshold }
	}

	valid_to_accept = {
		gold >= kehillah_loan_principal_value
		scope:employer = {
			is_alive = yes
			NOT = { government_has_flag = government_is_kehillah }
			NOT = { faith = root.faith }
			NOT = { exists = var:kehillah_loan_amount_owed }
		}
	}

	# Stays open exactly as long as the loan is outstanding -- see this
	# type's header for why the contract cannot distinguish repayment
	# from default at this point and deliberately does not try. The debt
	# now lives on task_contract_employer (the borrower), not the taker.
	valid_to_continue = {
		task_contract_employer = {
			exists = var:kehillah_loan_amount_owed
		}
	}

	valid_to_keep = {
		task_contract_employer = {
			NOT = { exists = var:kehillah_loan_amount_owed }
		}
	}

	on_create = {}

	# No longer originates the loan immediately -- sets a Stewardship-
	# banded starting tally (same three-band shape kehillah_translation_
	# contract's own on_accepted uses for Learning) and hands off to
	# events/kehillah_loan_events.txt's own three-stage challenge chain.
	# See this type's own header for the full account of why.
	on_accepted = {
		save_scope_as = task_contract
		task_contract_taker = {
			play_sound_effect = "event:/DLC/EP3/SFX/UI/Contracts/ep3_ui_contracts_accept_contract"
			if = {
				limit = { stewardship >= 16 }
				set_variable = { name = kehillah_loan_challenge_tally value = kehillah_loan_challenge_baseline_high }
			}
			else_if = {
				limit = { stewardship >= 10 }
				set_variable = { name = kehillah_loan_challenge_tally value = kehillah_loan_challenge_baseline_mid }
			}
			else = {
				set_variable = { name = kehillah_loan_challenge_tally value = kehillah_loan_challenge_baseline_low }
			}
			trigger_event = { id = kehillah_loan_challenge.0001 days = 5 }
		}
	}

	on_completed = {}

	on_invalidated = {
		task_contract_taker ?= {
			custom_tooltip = kehillah_loan_contract_concluded_tt
		}
	}

	should_show_toast_on_complete = no

	task_contract_reward = {
		# Defense in depth only -- see this type's header, the final
		# paragraph, for why this is deliberately inert.
		repayment_bookkeeping = {
			should_print_on_complete = no
			visible = no
			positive = yes
			effect = {}
		}
	}

	weight = {
		value = 0
	}
}

# EXOTIC GOODS -- source something rare the community's trade contacts
# can plausibly reach. v8 spec section 4c.
#
# SCOPE CUT, DOCUMENTED (spec 4c): no artifact reward. Verified (this
# file's own top header) that no real vanilla task_contract_reward block
# anywhere in the installed game applies a create_artifact-family effect

# runs in on_accepted, a structurally different place with different
# scope guarantees. Rather than force an artifact into a spot nothing
# vanilla actually does that, this is gold + opinion, exactly as the
# spec names as the acceptable fallback.
#
# STEWARDSHIP, NOT LEARNING, gates the outcome tier -- sourcing goods
# through trade contacts is a Stewardship skill in CK3's own vocabulary
# (see e.g. bandit_payment/harvest_sell_excess in the installed
# admin_contracts.txt pairing stewardship-flavored contract outcomes with
# gold). Three tiers, not two, because this is the one type with a real
# FAILURE state the spec explicitly asks for (positive = no, "no gold,
# smaller opinion penalty") -- and with no learning-style floor gating
# valid_to_create (spec doesn't ask for one here), the bottom tier is
# genuinely reachable, unlike the loan contract's dead reward key above.
# ---------------------------------------------------------------------
