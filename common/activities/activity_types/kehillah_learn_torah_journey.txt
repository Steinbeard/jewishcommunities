# Learn Torah -- the journey, as a real activity_type. ADDED 2026-09-15
# at user request, REPLACING kehillah_visit_library_interaction (common/
# character_interactions/kehillah_character_interactions.txt, RETIRED --
# see that file's own retirement note) the same day: "the interaction is
# awkward. Maybe we should make it another activity like bet din? But
# with more targets than just your home community" -- and separately,
# "studying should happen when you reach the target court, not when you
# return home."
#
# WHY THIS FIXES BOTH COMPLAINTS AT ONCE, NOT JUST THE SECOND ONE. The
# interaction's own hand-rolled start_travel_plan (its on_accept, now
# gone) already fired kehillah_learn_torah_journey.0001 on arrival, not
# on return -- mechanically it was never wrong on THAT specific point.
# But a real activity_type fixes the actual complaint underneath both:
# travel becomes visible and native (the Activities window, a real
# travel plan the player can see progressing, arrival/passive/active
# states) instead of a silent effect tucked inside accepting an
# interaction, AND the destination is no longer a single interaction
# target picked once -- it is a real, scored, re-rankable field of
# candidates every time the activity is planned, which is what "more
# targets than just your home community" asks for structurally, not
# just larger.
#
# HOST = THE TRAVELLER, SOLO, UNLIKE kehillah_bet_din_conference. Bet
# Din's host stays home (province_filter = capital) and guests travel TO
# them; this activity inverts that -- the host is the one travelling,
# to a location that is NEVER their own capital (is_location_valid
# below explicitly excludes it), and there are no guests at all
# (open_invite = no). This is the one structural way this activity
# genuinely cannot reuse Bet Din's own shape wholesale, and the reason
# host travel (not just guest travel) needs to actually work here --
# see the ONE REAL UNVERIFIED ASSUMPTION note below.
#
# WHY province_filter = all, DESPITE THE SCHEMA'S OWN WARNING ("almost
# certainly do not need to use it"). Every other named filter (capital/
# domain/realm/top_realm/holy_sites*/domicile*/top_liege_border_*/
# landed_title/geographical_region, common/activities/activity_types/
# _activity_type.info) resolves relative to the HOST's own realm or
# faith -- none of them can express "wherever any of sixteen scattered,
# independently-ruled Kehillah communities happens to be," which is
# exactly this mod's own map shape (registered communities have no
# shared de jure parent -- see common/landed_titles/kehillah_landed_
# titles.txt's own header on why the old d_kehillah_<region> duchies
# were removed). is_location_valid narrows the real candidate set back
# down to the ~16 communities in kehillah_registered_communities
# immediately, so the practical cost is bounded even though the nominal
# filter is not -- the same "bounded, not free" tradeoff this mod's own
# kehillah_bet_din_invite_rule_jewish_scholars/_adventurers already
# accepted for iterating every_independent_ruler (that file's own
# header note). ai_province_filter is deliberately NOT also `all` --
# see AI below.
#
# AI NEVER HOSTS THIS, ON PURPOSE. ai_will_do = 0 belt-and-braces with
# ai_province_filter = capital (cheap, and never actually valid per
# is_location_valid's own "not the host's own community" exclusion, so
# the AI's own province-scoring pass has nothing to do even if it runs
# at all) -- two independent reasons the AI can never actually host this,
# not just one, specifically because `all` is a real, acknowledged
# performance risk this mod does not want an AI evaluation loop anywhere
# near, on top of the same "a personal browsing/study action, not
# something the game's economy should depend on" reasoning kehillah_
# view_communities_interaction's own header already used for an
# identical ai_will_do = 0 call.
#
# THE ONE REAL UNVERIFIED ASSUMPTION, flagged rather than hidden: this
# whole design assumes the activity system automatically travels a HOST
# to a self-picked, non-capital, real location, and automatically
# returns them home once the activity completes, the same way vanilla's
# own Pilgrimage/Hunt/Tour activities are known to work for THEIR hosts.
# This mod's own confirmed-live travel evidence to date
# (docs/testing/2026-09-08-bet-din-conference-live-test-log.md) is for
# GUESTS travelling to a host's capital, not for a HOST travelling to a
# picked destination -- the general mechanism is standard, well-
# established CK3 activity behavior, not a guess invented for this file,
# but it has not been independently live-tested BY THIS MOD for the
# host-travels case specifically. Flagged here exactly the way this
# mod's own gui/scripted_widgets/ uncertainty was flagged before its own
# live-test closed it (docs/spec/gui-spike-community-list.md §4).
# =====================================================================

	# HOW CANDIDATES ARE SCORED/RANKED -- per user request ("scores based

	# guess. A second candidate route (unconditional custom_tooltip lines

	# failures_only above already uses for its own informational text)
	# was considered and deliberately NOT taken either: that field's own
	# real, confirmed rendering behavior is specifically "explain why a
	# candidate FAILED validity" (the "_showing_failures_only" convention
	# this file's own can_start_showing_failures_only is named for), not
	# a general-purpose always-shown breakdown surface -- stacking three
	# more never-failing custom_tooltip lines onto a VALID candidate's
	# own is_location_valid would be relying on that same mechanism
	# working somewhere its own naming does not actually promise it
	# does, which is a real guess this file is not making. The literal
	# per-track count therefore surfaces only once you have already
	# picked a destination and arrived -- kehillah_learn_torah_journey.
	# 0001's own three track options (events/kehillah_learn_torah_
	# journey_events.txt) each still name the specific work found there
	# -- not on the picker itself. A live-tested fix for the picker,
	# if this gap matters enough once seen in a real game, is a real

	# CONFIRMED SHAPE: every_in_list/every_in_global_list accumulating
	# into a script value's own running total via a plain `add` per
	# matching entry is real, shipped vanilla syntax -- game/common/
	# script_values/00_activity_values.txt's own petition_liege_county_
	# control_count_value ("value = 0  every_in_list = { list = X
	# add = 1 }") is the confirmed precedent; this is the identical shape
	# with `add` as a full inline value expression (itself a confirmed
	# generic capability of `add`) instead of a flat 1, and over
	# every_in_global_list instead of every_in_list, matching this mod's
	# own already-established every_in_global_list usage elsewhere. Since
	# at most one registered community's domicile can occupy any single
	# province, the limit below matches at most one entry in practice --
	# this is a sum over "zero or one" matches, not a real multi-entry
	# aggregation, written as a sum anyway because that is what the
	# confirmed vanilla idiom actually is.
	province_score = {
		value = 0
		every_in_global_list = {
			variable = kehillah_registered_communities
			limit = {
				exists = holder
				holder = { domicile.domicile_location = root }
			}
			add = {
				value = 0
				if = {
					limit = {
						holder = { primary_title = { is_target_in_variable_list = { name = kehillah_library_works target = flag:work_targum_onkelos } } }
						NOT = { scope:host = { is_target_in_variable_list = { name = kehillah_studied_works target = flag:work_targum_onkelos } } }
					}
					add = 1
				}
				if = {
					limit = {
						holder = { primary_title = { is_target_in_variable_list = { name = kehillah_library_works target = flag:work_mekhilta } } }
						NOT = { scope:host = { is_target_in_variable_list = { name = kehillah_studied_works target = flag:work_mekhilta } } }
					}
					add = 1
				}
				if = {
