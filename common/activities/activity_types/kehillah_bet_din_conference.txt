# Kehillah Bet Din Conference -- travelled-to gathering activity.
#
# Source of truth: docs/spec/v5-bet-din-conference.md, generalized to all
# four minhag regions by docs/spec/v6-minhag-regions.md section 4.
# Supersedes kehillah_shum_takkanah_decision (retired from common/
# decisions/kehillah_decisions.txt -- see that file's header) and its
# event kehillah_shum.0001 (events/kehillah_shum_events.txt -- deleted
# outright 2026-09-10, having been dead code, kept only for historical
# reference, since 2026-09-08; see common/scripted_triggers/kehillah_
# scripted_triggers.txt's retirement note on is_kehillah_shum_member_
# trigger for why keeping it around any longer was no longer possible
# once that trigger -- which its own trigger block still referenced --
# was itself retired).
#
# PART 1 STATUS (test build, 2026-09-08): the first custom
# activity_type this mod has built. Deliberately minimal next to
# vanilla's own activity_types (Hunt is 5,843 lines, Grand Wedding is
# 4,097) -- no pickable phases or options, no biome-conditional
# backgrounds, no pulse_actions catalog, no window_characters. v5 spec
# section 3 flags a custom activity_type as this feature's first-of-
# its-kind structural risk; the goal here is proving the activity
# fires, hosts, and resolves a docket correctly, not matching vanilla's
# production polish. NOT YET LIVE-TESTED as of this writing -- treat
# this file as unverified against a real boot until a dated log exists
# under docs/testing/, the same caution v4 spec section 2 applied to
# the Sh'um duchy nesting before it was confirmed live.
#
# GENERALIZED TO ALL FOUR MINHAG REGIONS, 2026-09-10 (v6 spec section 4),
# THEN REWORKED THE SAME DAY (v7 spec, docs/spec/v7-minhag-geographic-
# tagging.md) to read a different underlying data source. v5/Part-1's
# hardcoded Sh'um trio was first generalized to real de jure parentage
# (primary_title.de_jure_liege, the four d_kehillah_<region> duchies v6
# built) -- that worked, but those four duchies are GONE as of the same
# day's v7 pass (common/landed_titles/kehillah_landed_titles.txt's own
# header has the full account: de jure nesting cannot support founding a
# Kehillah anywhere, only at pre-authored locations). Every check and
# selection below now reads the geographic-tagging mechanism instead
# (kehillah_minhag variable, tagged onto real vanilla duchies by
# kehillah_tag_minhag_regions_effect, common/scripted_effects/kehillah_
# minhag_geography_effects.txt) via kehillah_has_known_minhag_region_
# trigger / kehillah_shares_minhag_region_trigger / kehillah_is_regional_
# greatness_leader_trigger / kehillah_region_can_field_bet_din_panel_
# trigger (common/scripted_triggers/kehillah_scripted_triggers.txt). The
# BEHAVIOR this activity provides is unchanged from the v6 generalization
# -- it still works identically for Western Ashkenaz's six members,
# Anglia's four, or Provence's four, and still correctly refuses to offer
# convening at all for Eastern Ashkenaz's two -- only what each trigger
# reads underneath changed, not what it answers.
#
# WHO CAN CONVENE. UPDATED 2026-09-15 at user request: any community whose
# real host geography resolves to a minhag region this mod tags at all
# (kehillah_has_known_minhag_region_trigger) AND whose region can field a
# full panel (kehillah_region_can_field_bet_din_panel_trigger, common/
# scripted_triggers/kehillah_scripted_triggers.txt -- REWRITTEN again
# later the same day, see THE PANEL below, so this no longer means "the
# region has >= 3 members"). The Greatness-leadership gate that used to
# sit alongside this (kehillah_is_regional_greatness_leader_trigger --
# "only the community currently greatest in its region may convene") is
# REMOVED: any member of a region, not only its Greatness leader, may now
# host. kehillah_is_regional_greatness_leader_trigger itself is left
# defined in common/scripted_triggers/kehillah_scripted_triggers.txt
# (still used elsewhere, e.g. events/kehillah_debug_events.txt's reports)
# -- only this activity's own gate on it is gone. The co-judge selection
# below is unaffected: it ranks candidates independently of the host's
# own rank, so it already worked the same regardless of whether the host
# itself was the region's leader. This also means, unlike a scripted
# decision, no separate "start" decision is needed -- the vanilla
# activity-hosting UI reads is_shown/can_start_showing_failures_only
# directly, the same way it does for Hunt or a Grand Wedding.
#
# THE PANEL. REWRITTEN 2026-09-17, replacing special_guests kehillah_
# bet_din_co_judge_1/2 outright, at user request following two separate
# live-tested failures of that design (both co-judge slots resolving to
# the SAME character -- first on Prague, then again on Worms after the
# first attempted fix; full account in this file's own git history and
# ROADMAP.md's "both co-judge slots resolving to the same character"
# entry) and a follow-up design question: "should [co-judges] be an
# invite? Would that require a total restructure?", answered "how about
# the two people who accept with the highest score become the co-judges?
# ... cap the number of people who can accept."
#
# WHY special_guests turned out to be the wrong tool, not just buggy in
# this one instance: a required special guest is picked ONCE, in advance,
# by select_character -- a single character, compelled to a yes/no
# decision, where a decline cancels the WHOLE conference (activity_type.
# info's own doc: "if a required guest declines... the activity
# invalidates automatically"). There is no built-in way to ask several
# candidates and take whoever says yes; select_character deals in exactly
# one committed answer per slot. Both live-tested bugs came from trying
# to make a SECOND such slot aware of the FIRST slot's own answer before
# either was final -- state that, in hindsight, was never reliably
# readable across two separate select_character evaluations.
#
# NOW: co-judges are open-invite guests like any other, drawn from the
# same three populations THE OLD DESIGN scored -- kehillah_bet_din_
# invite_rule_jewish_regional_leaders/_courtiers/_scholars/_adventurers
# (common/activities/guest_invite_rules/kehillah_bet_din_invite_rules.
# txt) -- each free to accept or decline on their own, capped the same
# way every other open-invite population already is, by max_guests below
# (the literal answer to "cap the number of people who can accept").
# Once the docket actually opens (kehillah_bet_din_open_docket_effect,
# common/scripted_effects/kehillah_bet_din_scripted_effects.txt), it
# ranks whoever is ACTUALLY THERE by kehillah_bet_din_judge_score_value
# (common/script_values/kehillah_script_values.txt) -- region-sharing
# community leaders scored far above everyone else, so a leader who
# attends always outranks a courtier or adventurer who also did, the
# same FAVORED-not-required property the old design had -- and the top
# two become kehillah_bet_din_judge2/judge3, read fresh, exactly once,
# from settled attendance. Both the eligibility test (kehillah_bet_din_
# eligible_judge_trigger, common/scripted_triggers/kehillah_scripted_
# triggers.txt) and the scoring are computed from real, already-resolved
# game state -- nobody else's still-pending decision -- which is what
# makes this immune to the class of bug that broke special_guests twice.
#
# QUORUM: if fewer than two eligible people actually show up, kehillah_
# bet_din_open_docket_effect invalidates the whole session outright
# rather than let the docket run short-handed -- see that effect's own
# header for why (~80 direct judge2/judge3 references across the case
# content, all written assuming a full panel; a real Beit Din needs three
# besides). can_start_showing_failures_only below still checks kehillah_
# region_can_field_bet_din_panel_trigger before planning even starts, the
# same as before -- a planning-time ESTIMATE of who could plausibly show,
# not a guarantee, since turnout can never be known until the docket
# actually opens.
#
# THE DOCKET. Three cases per session, each one its own activity phase,
# each DRAWN AT RANDOM from the cases this session has not heard yet --
# see the phases block below and kehillah_bet_din_draw_case_effect
# (common/scripted_effects/kehillah_bet_din_scripted_effects.txt). The
# draw-without-repeat machinery v5 Part 2 wants therefore exists now;
# what is still missing is Part 2's actual CASE CONTENT, which remains
# explicitly out of scope until docs/spec/v5-bet-din-conference.md
# section 5's case-idea draft exists. With only the three Part 1 cases
# in the pool, a session hears all three in a random order; adding a
# fourth is one more random_list entry and its events, nothing else.
# See events/kehillah_bet_din_events.txt for the cases themselves and
# the full per-judge skill-check design -- that is where the actual
# engineering risk this activity type exists to prove out lives, not in
# this file.
#
# UPDATED 2026-09-08 (docket loop fix): this file originally ran the
# docket as one phase and one unbroken event chain, which fired every
# event at once and left the activity unable to end. The phases block
# below carries the full account.
# =====================================================================

		# region_trigger (common/scripted_triggers/kehillah_scripted_
		# triggers.txt) reads the SAME "does this community's real host
		# geography fall inside a minhag region this mod tags" question
		# off the new geographic-tagging mechanism instead.
		kehillah_has_known_minhag_region_trigger = yes
		is_adult = yes
	}

	can_start_showing_failures_only = {
		NOT = { is_activity_type_on_cooldown = activity_kehillah_bet_din_conference }
		is_imprisoned = no
		custom_tooltip = {
			text = kehillah_requires_regional_panel_tt
			kehillah_region_can_field_bet_din_panel_trigger = yes
		}
	}

	is_valid = {
		scope:host = {
			is_alive = yes
			is_imprisoned = no
			government_has_flag = government_is_kehillah
		}
	}

	province_filter = capital
	ai_province_filter = capital
	is_single_location = yes
	max_province_icons = 1

	cooldown = { years = kehillah_bet_din_conference_cooldown_years }

	allow_zero_guest_invites = yes

	# LIVE-TEST FIX, 2026-09-17: this field was never set, which

	# own), phase_bet_din_case_1's on_phase_active therefore fired, and

	# the instant the activity started, before any invited guest who

	# months, tournament.txt/local_examination.txt: 1 month, camp_party.

	# difference: kehillah_bet_din_invite_rule_jewish_regional_leaders is
	# distance-bounded (same minhag region), but _scholars/_adventurers
	# (kehillah_bet_din_invite_rules.txt) draw from every_independent_ruler
	# worldwide by Learning/government alone, no distance bound, so guests
	# can be arriving from much farther than camp_party's 1-week case
	# assumes.
	max_guest_arrival_delay_time = { months = 3 }

	# REWRITTEN 2026-09-17 (THE PANEL, this file's own header, has the
	# full account): open_invite already covered scholars/adventurers
	# since 2026-09-09; now it ALSO covers same-region community leaders
	# and the host's own courtiers -- everyone who used to be reachable

	# are gone. can_be_activity_guest below is now the SAME test for
	# every candidate, judge-shaped or not: kehillah_bet_din_open_docket_
	# effect (common/scripted_effects/kehillah_bet_din_scripted_effects.

	open_invite = yes

	guest_invite_rules = {
		rules = {
			1 = kehillah_bet_din_invite_rule_jewish_regional_leaders

			4 = kehillah_bet_din_invite_rule_jewish_adventurers

		defaults = {
			1 = kehillah_bet_din_invite_rule_jewish_regional_leaders
			2 = kehillah_bet_din_invite_rule_jewish_courtiers
			3 = kehillah_bet_din_invite_rule_jewish_scholars

	# LIVE-TEST FIX, 2026-09-08: `always = no` here silently made the
	# activity unstartable -- the "Start" button in the planning UI did
	# nothing at all (no dialog, no logged error; can_start_showing_
	# failures_only had already passed to even reach this screen). Root
	# cause, found by checking every vanilla activity_type that also
	# defines special_guests (coronation, feast, wedding, tournament,
	# camp_party, chariot_race, debate, hike): every single one gives
	# can_be_activity_guest a real, permissive trigger -- NONE use
	# `always = no`. This activity no longer defines special_guests at
	# all (REWRITTEN 2026-09-17), but the finding stands as the reason
	# this field was never allowed to default to a bare gate again.
	#
	# LIVE-TEST FIX, 2026-09-11: live test showed a Catholic Franconian
	# duke ("Konrad of Luxembourg") arriving as an "Arrived" guest,
	# alongside ordinary non-scholar courtiers. Root cause: kehillah_
	# shares_minhag_region_trigger is PURELY geographic (common/scripted_
	# triggers/kehillah_scripted_triggers.txt) -- with no religion/
	# Kehillah-ness requirement of its own, an unguarded OR branch let any
	# ruler whose capital merely sat inside a minhag-tagged region satisfy
	# it alone. Fixed by requiring is_jewish_character_trigger as a
	# top-level AND for every candidate, and restricting the region-
	# sharing branch to is_ruler = yes -- both still true below.
	#
	# REWRITTEN 2026-09-17: this used to gate general activity-guest
	# eligibility, with the (former) co-judge select_character pools
	# re-deriving the identical three branches by hand elsewhere in this
	# file. Both now delegate to ONE shared trigger, kehillah_bet_din_
	# eligible_judge_trigger (common/scripted_triggers/kehillah_scripted_
	# triggers.txt) -- see its own header for the full account of why a
	# single definition replaced what used to be three. The body below is
	# otherwise unchanged from the 2026-09-11 fix: same branches, same
	# order, just named once instead of repeated.
	can_be_activity_guest = {
		kehillah_bet_din_eligible_judge_trigger = { HOST = scope:host }
	}

	# CAP, answering "can we cap the number of people who can accept" at
	# user request, 2026-09-17: max_guests is that cap. Raised 5 -> 6 now
	# that it covers EVERYONE (co-judge candidates included), not 3 open
	# seats plus 2 reserved special-guest ones -- reserved_guest_slots is
	# gone along with those slots, nothing left to reserve room for.
	# Deliberately still bounded, not unbounded: a Beit Din is a docket of
	# specific named judges plus a few onlookers, not an open-ended
	# assembly, and vanilla's own activity_type.info documentation warns
	# against an uncapped guest list for the same travel-cost reason this
	# file's guest_invite_rules already cite for staying bounded to
	# every_independent_ruler/every_courtier rather than every character
	# in the world.
	max_guests = 6

	# =================================================================
	# THE DOCKET -- ONE CASE PER PHASE.
	#
	# LOOP-BUG FIX, 2026-09-08. This block previously held a SINGLE
	# phase whose on_phase_active fired case 1's host event, and every
	# event from there chained straight into the next one -- so all ten
	# events of the whole docket resolved inside one day. Worse, nothing
	# in this file ever called progress_activity_phase_after, which is
	# the one thing that ends a phase: every vanilla activity_type calls
	# it from on_phase_active or on_enter_phase (feast.txt, wedding.txt,
	# coronation.txt, tournament.txt, local_examination.txt -- checked,
	# no exceptions). Without it the single phase never ended, the
	# activity never reached completion, and the host was stuck in a
	# conference that had already said everything it had to say.
	#
	# Now: kehillah_bet_din_docket_case_count (3) predefined phases, one
	# case each, and the case is DRAWN AT RANDOM from those the session
	# has not heard yet (kehillah_bet_din_draw_case_effect, common/
	# scripted_effects/kehillah_bet_din_scripted_effects.txt -- see its
	# own header for the draw and the "not yet chosen" bookkeeping). The
	# phase count is what makes the docket end after three, and the
	# activity's completion is what pays out the session score.
	#
	# WHY THREE LITERAL PHASES rather than one phase that loops three
	# times: a phase is CK3's own unit of "part of an activity that
	# starts, runs a while, and finishes", and it is the only thing the
	# engine will advance and eventually complete on its own. Three
	# phases also make the docket legible in the Activities window
	# (F9 shows "Current Phase: The First Case"), which one repeating
	# phase would not. Vanilla precedent for several predefined,
	# same-location, purely sequential phases: local_examination.txt
	# (assembly / preparation / examination, is_single_location = yes).
	#
	# Each phase is identical apart from its order and, for the first,
	# the one-time session setup. on_phase_active runs once per
	# attending character, so everything here is guarded to scope:host
	# (camp_party.txt's precedent) -- both so the draw happens once and
	# so the two co-judges cannot each reset the phase timer after the
	# host's draw has already shortened it.
	# =================================================================
	phases = {
		phase_bet_din_case_1 = {
			is_predefined = yes
			order = 1
			location_source = pickable

			on_phase_active = {
				if = {
					limit = { this = scope:host }

					# Ceiling first, draw second: the draw may shorten this
					# phase (if no case was eligible) and must not be
					# overwritten by the ceiling afterwards.
					scope:activity = {
						progress_activity_phase_after = { days = kehillah_bet_din_case_phase_days }
					}

					kehillah_bet_din_open_docket_effect = yes

					# QUORUM GUARD, ADDED 2026-09-17: kehillah_bet_din_open_
					# docket_effect calls invalidate_activity itself if fewer
					# than two eligible attendees showed up (its own header
					# has the full account), but that alone does not stop
					# THIS same tick from also drawing a case for a docket
					# that no longer has judges to hear it -- invalidate_
					# activity and this sibling call are two separate
					# effects in the same on_phase_active body, not a
					# parent/child pair, so nothing here would otherwise
					# short-circuit the second one. kehillah_bet_din_judge3
					# only exists if quorum was met (set inside kehillah_
					# bet_din_open_docket_effect), so its existence is a
					# direct, reliable proxy for "did the session actually
					# open."
					if = {
						limit = { exists = scope:activity.var:kehillah_bet_din_judge3 }
						kehillah_bet_din_draw_case_effect = yes
					}
				}
			}
		}

		phase_bet_din_case_2 = {
			is_predefined = yes
			order = 2
			location_source = pickable

			# Same "let the phase become active promptly" hop
			# local_examination.txt uses on every phase after its first --
			# there is no travel between phases here (is_single_location =
			# yes), so nothing else would move the docket off the passive
			# state between cases.
			on_enter_phase = {
				if = {
					limit = { this = scope:host }
					scope:activity = {
						progress_activity_phase_after = { days = 1 }
					}
				}
			}

			on_phase_active = {
				if = {
					limit = { this = scope:host }
					scope:activity = {
						progress_activity_phase_after = { days = kehillah_bet_din_case_phase_days }
					}
					kehillah_bet_din_draw_case_effect = yes
				}
			}
		}

		phase_bet_din_case_3 = {
			is_predefined = yes
			order = 3
			location_source = pickable

			on_enter_phase = {
				if = {
					limit = { this = scope:host }
					scope:activity = {
						progress_activity_phase_after = { days = 1 }
					}
				}
			}

			on_phase_active = {
				if = {
					limit = { this = scope:host }
					scope:activity = {
						progress_activity_phase_after = { days = kehillah_bet_din_case_phase_days }
					}
					kehillah_bet_din_draw_case_effect = yes
				}
			}
		}
	}

	# The docket closes here, not in an event chain. kehillah_bet_din.
	# 0099 reads global_var:kehillah_bet_din_session_score -- the sum of
	# the three cases' verdict tiers -- and applies the session's own
	# reward on top of the per-case effects, then clears the session
	# scratch state. Guarded to the host: on_complete, like
	# on_phase_active, runs once per attending character, and the closing
	# event belongs to the convening leader alone (the co-judges' own
	# leave-taking is that event's text, not a second copy of it).
	on_complete = {
		if = {
			limit = { this = scope:host }
			trigger_event = kehillah_bet_din.0099
		}
	}

	# TRAVEL PULSE, ADDED 2026-09-09 at user request ("travel ticks").
	# root here is whichever character is currently travelling TO this
	# conference (activity_type.info: "root = character in this phase"),
	# so this fires for a travelling co-judge or an accepted open-invite
	# guest alike -- the host does not travel (the conference is hosted
	# at the host's own capital; see this file's province_filter above),
	# so scope:host never sees this fire on themselves.
	#
	# Nothing fired here before this: this file's own header calls out
	# "no pulse_actions catalog" as a deliberate Part 1 scope cut, and
	# on_travel_state_pulse specifically was never defined at all, so a
	# co-judge's real, live-tested ~12-day journey to Worms (docs/
	# testing/2026-09-08-bet-din-conference-live-test-log.md) passed in
	# total silence. kehillah_bet_din_travel_pulse_effect (common/
	# scripted_effects/kehillah_bet_din_scripted_effects.txt) gates its
	# own chance internally (not every pulse tick should produce a
	# popup) and picks one of a small set of flavor vignettes
	# (events/kehillah_bet_din_travel_events.txt) -- Part 1 minimal, the
	# same spirit as the rest of this activity. The "no pulse_actions
	# catalog" cut itself is superseded immediately below, 2026-09-09.
	on_travel_state_pulse = {
		kehillah_bet_din_travel_pulse_effect = yes
	}

	# GUEST PULSE ACTIONS, ADDED 2026-09-09 at user request ("make it
	# interesting to be a guest at a bet din activity"). Before this, an
	# attending guest had nothing to do during an active case phase --
	# the docket's own three events per case are all gated to root = the
	# convening leader or judge2/judge3 specifically, never a plain
	# attendee, so a co-judge or (per the same conversation's earlier
	# widening) an accepted scholar/adventurer guest just sat through the
	# phase. See common/activities/pulse_actions/kehillah_bet_din_pulse_
	# actions.txt for the three entries and their own header for the
	# full account -- one Prestige/opinion reward weighted toward
	# Learning, one two-character opinion swing for texture (not every
	# pulse should be a reward), one Prestige reward specifically for
	# attending Jewish adventurers.
	pulse_actions = {
		entries = {
			kehillah_bet_din_pulse_citation
			kehillah_bet_din_pulse_disagreement
			kehillah_bet_din_pulse_renown
		}
	}

	# UPDATED 2026-09-09 at user request ("AI who have the option to host
	# a bet din should do it"). This field is NOT an arbitrary weight --
	# activity_type.info's own doc is explicit: "This value will then be
	# used as a percent chance to be hosted, such that 0 will never be
	# hosted and 100 will always be hosted," AFTER this activity has
	# already been chosen as the highest-scoring one available that
	# check. 40 meant that even when the Bet Din was the AI's best
	# available option, it still had better than even odds of just not
	# happening. 100 is the strongest lever this field gives -- given
	# selected, it now always follows through.
	#
	# What 100 does NOT do: guarantee this activity gets selected over
	# competing ones (Hunt, Feast, etc.) in the first place -- that is a
	# separate, relative comparison of every eligible activity_type's own
	# score this file cannot unilaterally win. STALE COMMENT REMOVED
	# 2026-09-15: this used to say eligibility was "the current Greatness
	# leader among the three Sh'um communities... a narrow, infrequent
	# eligibility window" -- both the Sh'um-only scope and the Greatness-
	# leadership gate are long gone (WHO CAN CONVENE, this file's own
	# header), so is_shown/can_start_showing_failures_only no longer
	# narrows things nearly that much; any member of a known minhag region
	# with a fillable panel is now eligible, competing against a fuller
	# routine slate than this comment used to assume.
	ai_will_do = {
